# 竞技场（战术对抗赛）协议研究（2026-10-21 实测定案）

> 结论：**战术对抗赛没有独立的「结算」请求**。战斗由服务端演算（`IsServerRunBattle`），
> 结果直接随 `arena/enterbattle(22004)` 的响应返回。原先记的「缺结算协议」是误解。

## 1. 接口与流程

```
arena/enterlobby(22000)          → 大厅信息：我的排名、对手列表、是否服务端演算
arena/opponentlist(22003)        → 刷新对手列表（可跳过，enterlobby 已带）
arena/syncechelonsettingtime(22016) → {EchelonSettingTime} 防守编队最后修改时间
arena/enterbattle(22004)         → 发起战斗，响应里直接带战果
arena/dailyreward(22009)         → 每日奖励领取（无业务字段）
arena/cumulativetimereward(22008) → 累计时间奖励领取（无业务字段）
```

## 2. enterbattle 请求

```json
{"Protocol": 22004, "OpponentAccountServerId": 10008768637, "OpponentIndex": 0, "OpponentRank": 64}
```
- `OpponentAccountServerId` / `OpponentRank` 取自 `enterlobby.OpponentUserDBs[]`
- `OpponentIndex` 是列表下标（0 = 第一个对手）
- 消耗 1 张战术对抗赛挑战券（Currency **7**）

## 3. enterbattle 响应（关键结构）

```
ArenaBattleDB
  Season / Group / BattleStartTime / BattleEndTime / Seed
  AttackingUserDB / DefendingUserDB        // 双方完整阵容（含装备、技能等级）
  BattleSummary                            // ← 战果在这里
    Winner: "Group01" | "Group02"
    EndType / EndFrame                     // 结束方式与帧数
    IsDefeatBattle: bool
    Group01Summary / Group02Summary        // 每队 TeamId、Leader、AssistRelations
    ArenaSummary { ArenaMapId, EnemyAccountId, EnemyAccountLevel }
ArenaPlayerInfoDB                          // 赛后状态：CurrentRank / SeasonRecord / AllTimeRecord / BattleEnterActiveTime
VictoryRewards / SeasonRewards / AllTimeRewards
BattleSetting / BattleServerError
AccountCurrencyDB                          // 赛后货币快照（券数可直接读）
```

**实测样本（2026-10-21 15:59:28，本号）**
- 我方 `AttackingUserDB.Rank = 89`，对手 `DefendingUserDB.Rank = 64`
- `Winner = Group02`，`EndFrame = 916`，`EndType = 1`，`IsDefeatBattle = false`
- 赛后 `ArenaPlayerInfoDB.CurrentRank` 仍是 **89**（没升名次）

**已定案（用角色 ServerId 对齐）**：`Group01Summary.Heroes[].ServerId = [239093, 770403, 2212876, 2737878]`
与 `AttackingUserDB.TeamSettingDB.MainCharacters` 完全一致 → **Group01 = 攻方（我方）**，Group02 = 守方。
所以本场 `Winner = Group02` 是**判负**，名次自然不变（输掉不改名次）。

## 4. 「跳过对战过程」设置的协议含义

`enterlobby` 响应里有 **`IsServerRunBattle`** 字段。开启该设置后为 true：
服务端直接演算整场战斗并返回 `BattleSummary`，客户端只播个结果界面，不跑战报。
所以抓包只会看到 `enterbattle` 一次调用 —— **不是漏抓**。

## 5. 自动战斗可行性（结论：现在就能做）

```
loop:
  lobby = enterlobby()                      # 拿 OpponentUserDBs + 券数(Currency 7)
  if 券 == 0: break
  挑一个对手（按 Rank 最靠后 / 战力最低）
  res = enterbattle(opponent)
  记录 res.BattleSummary.Winner 与赛后 CurrentRank
```
- 不需要 `opponentlist`（`enterlobby` 已带对手列表，省一次请求）
- 不需要模拟战斗过程，不存在"战斗校验"环节
- 判胜负只读 `BattleSummary.Winner` 与 `CurrentRank` 变化

## 6. 副产品：抓包响应可离线解密

`ba_crypto.decrypt_response(capture 文件里的 resp_body)` 直接可用——响应密钥明文附在密文尾部
（`BASE64: → gzip → b64 → [ct || key32]`），不依赖在线会话。
本次抽样 77 条响应，**68 条成功解出**（失败的 9 条是静态资源/空包）。

> 这条推翻 10-19 报告里「本次仅解请求侧」的结论：以后所有历史抓包都能补出响应结构，
> 不必再"另起会话采 key"。

## 7. 参考：BAAS（图像识别）怎么清票

源码 `module/arena.py` + `core/config/default_config.py`（2026-10-21 拉取）：

```
进战术对抗赛 → OCR 读券数(x/5)
  券 == 0                → 领「时间奖励」+「每日奖励」→ 结束
  ArenaStopFightWhenRank1 且 rank == 1 → 只领奖，不打
  否则：
    选第 ArenaComponentNumber 个对手（1~3，默认 1）
    OCR 对手等级；若 对手等级 + ArenaLevelDiff(默认 0) <= 自己等级 → 打
    否则点「更新列表」重刷，最多 maxArenaRefreshTimes 次（默认 10），刷不到就硬打
    开打前 check_skip_button()：确认「跳过战斗」是开的，否则点开
    检测 arena_battle-win / lost 结束画面 → 回大厅
  剩余券 > 1 → next_time = 55 秒（= 30s 待机 + 动画缓冲），等调度器再调一次（**一次只打一场**）
  剩余券 == 1 → 打完领奖收尾
```

要点：
- `ArenaComponentNumber = 1` 对应 y=261，是**最上面那张卡**；对手列表按名次从高到低排
  （抓包样本 `OpponentUserDBs` 的 Rank 是 [67, 72, 83]），所以 **默认打的是「能打到的最高排名」**，不是软柿子
- 等级校验（`对手等级 + ArenaLevelDiff <= 自己等级`）在**满级服恒成立**（人手 90 级），
  实际效果是「刷 10 次列表后照样打第一位」——10 次刷新纯属浪费
- **胜负只用于识别结束画面**，不做策略：输了也照样继续清票
- 结算靠「跳过战斗」开关，否则要等完整战报动画（我们已确认：开关对应 `IsServerRunBattle`，服务端演算）
- `purchase_arena_ticket_times` 默认 `0`：不花青辉石买票

对照我们（协议）：
- 券数：`AccountCurrencyDB.CurrencyDict["7"]`，不用 OCR
- 对手等级/排名：`enterlobby.OpponentUserDBs[].Level / Rank`，不用 OCR
- 胜负：`ArenaBattleDB.BattleSummary.Winner`，不用图像识别
- 刷新对手：`arena/opponentlist(22003)` 一次请求，比点按钮刷更省

## 8. 机制补充（社区资料 + 实测对齐）

- **30 秒待机**：国服 2025-11-05 维护公告把「待机时间」由 60 秒改为 **30 秒**。
  实测吻合：本场 `BattleStartTime = 15:59:27.95`，响应里 `ArenaPlayerInfoDB.BattleEnterActiveTime = 15:59:57.95`
  —— **正好 +30s，这就是「下一次可进战」的时间戳**，自动化直接读它，不用自己算 CD。
  ⚠️ master 反馈「赢和输的待机好像不一样」：本样本是失败局（30s）。若胜局不同，服务端同样会反映在这个字段里，
  实现上不需要区分；想确证可以等一场胜利样本对比。
- **挑战券**：每日 5 张、4:00 重置；60 青辉石可补 5 张（无上限）。券 ID = Currency **7**。
- **可攻击范围**：只能打「当前排名 × 0.7 ~ 自己排名 - 1」区间内的玩家（例：第 11 名最高能打第 7 名），
  所以对手列表里 Rank 一定 ≤ 自己的 Rank。`OpponentUserDBs` 按名次从高到低（Rank 数字小 → 大）排列。
- **名次变化**：赢 → 与对手互换名次；输 → 名次不变（实测一致：rank 89 输给 rank 64 后仍是 89）。
- **防守**：防守成功给 3 战术奖币，每天上限 30。
- **对手情报（服务端裁剪过）**：`OpponentUserDBs[].TeamSettingDB` 里只有 **1 名前锋（队长）+ 2 名后排**是真实数据，
  另外 3 个前锋槽位是空壳（`UniqueId=0 / StarGrade=0 / Level=0`）——是服务端裁剪，不是客户端隐藏。
  可见的这 3 人数据很全（学生 UniqueId、星级、等级、Ex/被动技能、装备 Tier、专武、好感、站位、CombatStyle）。
  开战后 `enterbattle` 响应里的 `DefendingUserDB` 才下发完整 4+2（本次样本：前排 10074/10011/10037/10100，后排 20000/20027），
  但那时券已经花掉了。
  → **强度分只能基于 3 个可见角色估算，适合当弱权重，不能当主依据**；主依据仍是名次。
- **列表自动刷新**：`AutoRefreshTime`（实测每 2 分钟），离开大厅也会刷新。

## 9. 自动清票实现（2026-10-21 WebUI 接入）

**调用序列（必须完整）**：`enterlobby(22000)` → `syncechelonsettingtime(22016)` → `enterbattle(22004)`。
少了中间的同步，服务端直接回 **`协议错误 21017`**（实测：不带 sync 失败、带上即成功）。

**选人策略（第一版，照 BAAS）**：`OpponentUserDBs` 按「等级升序 → 名次升序」排序取第一个。
满级服等级恒同，等价于「打名次最高的那个」。不做强度分（选人阶段只看得见队长 + 2 后排，见 §8）。

**节奏**：每场之后服务端给 `BattleEnterActiveTime`（+30s 待机），清票线程读到就等，
等待期间其他模块照常发请求（请求串行走会话锁，不冲突）。

**实测（2026-10-21 16:31）**：目标 R67（Lv90），`Winner=Group02` 判负，名次仍 R89，`EndFrame=1165`。
失败调用不扣券（券数 3 → 3），成功才扣。

**踩坑**：券数走 loginsync 货币字典（Currency 7），有 60s 缓存；打完一场要清缓存再读，
否则会出现「打了券没少」的假象。
