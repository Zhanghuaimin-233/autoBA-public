# 悬赏通缉（2026-10-17 实现）

## 1. 基础数据

| 项 | 值 |
|---|---|
| 列表接口 | `/api/weekdungeon/list`（23000，无请求字段） |
| 扫荡接口 | `/api/contentsweep/request`（27000） |
| 扫荡请求 | `{"Content": 3, "StageId": 30110, "Count": 6, "EventContentId": 0}` |
| 票 | `Currency 22 = ChaserTotalTicket`，每日补 6 张 |
| 三张图 | ChaserA **悬赏通缉：高架公路** 30101–30110、ChaserB **悬赏通缉：沙漠铁路** 30201–30210、ChaserC **悬赏通缉：讲堂** 30301–30310 |

票是三张图共享的一个池（Currency 22），不是每图各 6 张。

## 2. 「最新关」怎么判

服务器**不提供关卡目录**，`weekdungeon/list` 只返回：

- `WeekDungeonStageHistoryDBList`：已通关关卡 + 三星记录
- `AdditionalStageIdList`：目前恒空

关卡目录在客户端表 `WeekDungeonExcel`。地图名取自 `LocalizeExcel` 的三条原文（`悬赏通缉：高架公路 / 沙漠铁路 / 讲堂`），关卡难度在国服用**字母 A–J**（`Difficulty` 1–10，J 为当前最新），界面上显示成 `30110（J）`；若以后开到第 11 关，自动变成 `30111（K）`。

所以每张图算两个值：

- **已开放最高关** = 表内该类型最大 StageId
- **可扫最高关** = 通关历史里三星（Clear/AllAlive/ClearTimeInSec 全 1）的最大 StageId

规则（参考 autopcr `sweep.py` 的「非最高不扫荡」）：

| 情况 | 行为 |
|---|---|
| 已开放 > 可扫（新关没三星） | 默认停止该图，提示「最高关 30111 未三星」；勾选强制执可继续刷旧关 |
| 数据版本落后（90007 探针） | 默认锁定扫荡，提示先更新 tables；可强制执 |
| 历史出现表外 StageId | 判定本地表过期，默认锁定；可强制执 |
| 两者一致 | 正常扫荡 |

表过期时无法提前知道新关，靠 `/api/resource/status` 的版本探针预警（见 `docs/数据版本校验.md`）。

## 3. 前端交互

- 三张图各一个数字输入框（票数），默认 0
- 合计 ≤ 6：超过时按钮禁用并标红；小于 6 时提示「未满，仍可执行」
- 「一键扫荡」→ 页内确认条（列出每图票数与目标关）→ 执行
- 执行后逐图日志：地图、关卡、次数、券余、奖励（ClearParcels 聚合，最多显示 6 项）

## 4. 后端接口

| 接口 | 说明 |
|---|---|
| `GET /api/bounty/state` | 三图状态（released / sweepable / newNotCleared / unknownStages）+ 版本状态 |
| `POST /api/bounty/sweep` | `{"counts": {...}, "force": false}`，校验合计 ≤ **当前余额** |

**票数余额**：loginsync 的 `AccountCurrencySyncResponse.AccountCurrencyDB.CurrencyDict["22"]` 就是实时余额（每日 6 是补充量不是上限，月卡可超 6，上限 30）。state 返回 `tickets`，sweep 前校验 `合计 > 余额` 直接 409，不发请求。

> 坑：`login_sync` 的 `SyncProtocols` 必须照抄客户端的完整列表——只请求 [20000,1003,2000] 时 `AccountCurrencySyncResponse` 会返回**空 CurrencyDict**（全 0），看起来像"票用完了"。

返回的 `steps` 里带每图的 `tickets`（扫荡后 Currency 22）和 `rewards`。

## 5. 验证边界

- 状态读取、分配校验、确认条均已实跑验证
- **未执行真实扫荡**，票未消耗
- 扫荡失败（如票不足、关卡未三星）时停止后续步骤，已完成的保留
