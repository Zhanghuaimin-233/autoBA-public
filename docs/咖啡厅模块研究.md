# 咖啡厅模块研究笔记（2026-10-14 初版 / 10-15 数据挖掘定案）

> 数据源：历史抓包双向解码（cafe/ack ×6、cafe/interact ×30、cafe/receivecurrency ×2、cafe/summoncharacter ×4，共 42 响应样本；原始提取见 cafe_resp_parsed.jsonl）。
> 状态：接口结构、产出结构、摸头数值均已定案；送礼接口、产出累积公式待实测。

## 0. 咖啡厅双厅规则

- CafeDBId = **AccountId × 10 + 厅号**：`100000000001`（1 号厅）、`100000000002`（2 号厅）。
- 2 号厅（CafeId 2）需推图/条件解锁；两厅独立产出、独立访客。

## 1. 接口清单与请求模板

### cafe/ack（20001）— 咖啡厅状态确认
```json
{"Protocol": 20001, "CafeDBId": 100000000001, "Resendable": true, "Hash": ..., "IsTest": false, "AccountId": ..., "OSType": 2}
```
响应：`CafeDB`（完整咖啡厅状态）。

### cafe/interact（20006）— 摸头/互动
```json
{"Protocol": 20006, "CafeDBId": 100000000001, "CharacterId": 10060, ...标准头}
```
- `CharacterId` = 学生 **UniqueId**（10000 系）。
- 响应：`CafeDB`（访客 LastInteractTime 实时更新）+ **`CharacterDB`（单数！被摸学生的完整状态，FavorRank/FavorExp 为摸后绝对值）** + `ParcelResultDB`。
- `ParcelResultDB` = AccountCurrencyDB 货币快照（30/30），**摸头不发任何奖励**。
- **摸头好感 = 精确 +15（10-15 跨请求差分定案）**：圣娅 50→65→80、爱理 10→25→40（跨 3 天）、若藻 232→247、渚 250→265。
- **CD 判据**：`CafeDB.CafeVisitCharacterDBs["<UniqueId>"].LastInteractTime`（30/30 摸头后立即写入，跨天样本正常累积）；CharacterDB 内**没有** LastInteractTime 字段。
- ⚠️ 学生到好感星级上限（1★/2★=Rank10，3★=20，4★=30，5★=100）后摸头 **+0**（10-15 二次实证：惠/巴/月咏/爱丽丝（女仆）/真白/三森 六个 3★ Rank20 Exp0 学生摸后纹丝不动）。

### cafe/receivecurrency（20013）— 领取产出（信用点/体力）
```json
{"Protocol": 20013, "AccountServerId": 10000000000, "CafeDBId": 0, ...标准头}
```
- **CafeDBId = 0 表示领取全部咖啡厅的产出**。
- 响应：`CafeDBs`（列表，两厅状态）+ `ParcelResultDB`（信用点/青辉石入账走 DisplaySequence）。

### cafe/summoncharacter（20015）— 招待券邀请学生
```json
{"Protocol": 20015, "CafeDBId": 100000000001, "CharacterServerId": 1753765, ...标准头}
```
- ⚠️ 用 **CharacterServerId**（ServerId，如 1753765），**不是** UniqueId——与 interact 的字段不同！
- 招待券 20 小时冷却（`LastSummonDate` 判 CD）；4 次实测：10-12 20:36 两厅 → 10-13 17:22/17:25 再用，间隔 ~20.8h > 20h ✓。
- 响应：`CafeDB` + `CafeDBs`。实测链路：summon 请求 CharacterServerId=2998847 → 后续 interact 用 UniqueId=10111（同一学生）✓。

## 2. CafeDB 结构（核心字段）

```
CafeDBId / CafeId / AccountId
CafeRank = 10                       // 咖啡厅等级（推图获取升级核心）
LastUpdate / LastSummonDate / IsNew
CafeVisitCharacterDBs = { "<UniqueId>": {UniqueId, ServerId, LastInteractTime} }   // 当前来访学生
FurnitureDBs = [{Type:13, ServerId, UniqueId, StackCount, Location(2/3/4), PositionX, PositionY, Rotation, ItemDeploySequence, CafeDBId}]  // 家具摆放（1 号厅实测 57 件）
ProductionAppliedTime
ProductionDB = { CafeDBId, ComfortValue, AppliedDate, ProductionParcelInfos }
```

- **ProductionDB.ProductionParcelInfos（10-15 定案，字段实名非 ProductionParcels）**：
  ```json
  厅1: [{"Key": {"Type": 2, "Id": 1}, "Amount": 0}, {"Key": {"Type": 2, "Id": 5}, "Amount": 0}]
  厅2: [{"Key": {"Type": 2, "Id": 1}, "Amount": 0}]
  ```
  Type 2 = Currency：厅 1（舒适度 5500）产信用点(Id 1) + 青辉石(Id 5)；厅 2（舒适度 5000）只产信用点。6 个 ack 样本 Amount 全为 0（都在领取后/刚应用时点），**累积中的 Amount>0 样本未抓到**——推测服务端实时计算累积、领取后清零，待实测确认。
- `ComfortValue`（舒适度）决定体力/信用点生产效率；家具稀有度：白20/蓝50/金120/紫350。
- **访客机制（10-15 数据实证）**：
  - 每厅常态 5 名访客，summon 后 6 名。
  - **未招募学生也会来访**（ServerId=0：10026、10084、10116）——摸头无 CharacterDB 增益（与日程莲见 delta 0 同理）。
  - **存在跨天常驻访客**：10110（ServerId 2969203）、23000（ServerId 550688）三天三批访客列表恒定在场——刷新**不是全量替换**，具体轮换规则待更多样本。
  - 访客实例以 (UniqueId → ServerId) 标识，同一学生跨批次 ServerId 不变。

## 6. 双厅与同位体规则（2026-10-17 社区核实）

来源：萌娘百科「蔚蓝档案」咖啡厅段、巴哈姆特基础系统帖、bluearchive.gg Cafe Guide、namu wiki Blue Archive/Cafe、PTT「100羁绊讲解」。

- **占位是人物级（含换装）**：同一个学生（含不同形态）不会同时出现在两厅；同一厅也只能存在一种造型。用邀请券把某形态叫到另一厅，原厅里同人的那个形态会消失（被顶掉/移走）。
- **邀请可以跨厅移动**：从 A 厅的邀请列表里能看到正在 B 厅的同一学生，邀请后 B 厅消失、A 厅出现（namu wiki 明确描述）；同厅已有的学生不在邀请列表里，同人异形态除外（可换装）。
- **摸头 CD 按「厅 × 访客实例」算，不按人物**：`LastInteractTime` 存在每厅的 `CafeVisitCharacterDBs[UniqueId]` 上。PTT 实操贴：「下午三點羽留奈到 2 樓，先到 2 樓摸一次，然後到 1 樓用招待券邀請，這樣可以再摸一次」——换厅会重置摸头机会。社区据此算出一名学生一天最多 8 次（两厅各 4 次/12h 循环），走运可到 10 次。
- **羁绊按形态独立**：bluearchive.gg 明确 “Alt students count as completely different students, and thus their bond levels are not shared”，只有羁绊带来的属性加成共用。
- **邀请券**：每厅独立 20h CD；邀请的学生停留到下次刷新（4:00/16:00），刷新即消失——所以最佳时机是刷新后立刻用，12h 内可摸满 4 次。

## 7. 一键摸头 + 邀请（2026-10-17 实现）

**选择顺序**：咖啡厅卡片内有**独立的选择器**（与日程的指定学生互不影响，分别存 `localStorage: autoba.cafeSelected` / `autoba.selected`）。勾选先后即优先级，列表里带序号，上方 chip 条可用 ↑↓ 调整；日程的选择器不显示序号。该顺序是咖啡厅券位的分配依据。

**券位分配**（每厅 20h 一张，独立）：
1. 先按顺序，把「未在任一厅」的目标逐个补进券位；
2. 券还有剩，就按顺位给「已在厅」的目标各挪一次厅（挪厅重置摸头 CD，多摸一次）；
3. 券还有剩，再回头挪同一目标第二次（单人冲刺场景）。
4. 两个券位只有 2 张，方案生成时枚举分配顺序，按「总步数 → 高顺位学生拿到的次数」排序取最优。

**同人占位**：邀请会顶掉同人的其他形态（人物级占位）。若被顶的形态也是「未满」的指定学生，跳过该候选、顺延下一位。

**次数模型**：立即摸头次数 = 在场指定学生数 + 可用券位数。例：1 人未在厅=2 次；1 人自然刷到=3 次；2 人都在厅=4 次（2 免费 + 2 挪）。

**执行顺序**：先摸遍两厅所有「已拥有且未满」的访客，再按方案逐条「邀请/挪厅 → 立刻摸一次」。邀请失败即停止后续邀请（券状态未知），已完成的摸头保留。

**数据来源**：双厅状态取自 `loginsync(1017).CafeGetInfoResponse.CafeDBs`；`cafe/ack(20001)` 是状态确认接口（服务端要求 `IsNew=true`），不能当读取用。
