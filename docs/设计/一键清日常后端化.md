# 一键清日常后端化

> **状态**：已实现 ｜ **日期**：2026-10-28
> **背景**：项目自检报告的 P0-4 —— 一键清原来跑在前端 `runAllDaily()` 的 `for` 循环里，刷新/断网/关页面即中断且无状态可查；同时段所有请求挤在 `_sess_lock` 上，页面表现为卡死。
> **复核**：2026-10-28 在项目更新（签名转纯 Python、文档重组）后重核，10 个模块接口、10 个前端函数、`_arena_clear`、`skipped` 语义均未变动，事实基础仍成立；新增 §2.3「`stopped` 语义混用」为前置项。
> **实现**：见 §8（与设计稿的差异清单）。

## 1. 目标与非目标

**目标**

- 一键清在后端执行，浏览器关掉/刷新不影响
- 有结构化执行状态：每步状态（成功/跳过/失败）、耗时、日志，刷新后可恢复
- 顺序由 `ui_state.json` 的 `moduleOrder` 决定，不再依赖前端 DOM
- 引入「跳过」与「失败」的正式区分（沿用 2026-10-26 加的 `skipped` 语义）

**非目标（本期不做）**

- 不解锁粒度问题（项目自检报告 P1-8）：清理期间其他接口仍会排队，但轮询接口刻意不碰会话锁
- 不做定时自动执行（autopcr 的 cron 路线，另议）
- 不做断点续跑（中止后从头再来，与 autopcr 一致）
- 不引入 autopcr 那套 `Module` 基类 + 装饰器框架：10 个模块单账号，框架成本大于收益

### 2.1 学生选择列表（缺数据）

`schPicker` 只在 `localStorage['autoba.selected']`，后端拿不到；`cafePicker` 虽有 `onChange → savePrefs({cafeStudents})`，但当前 `ui_state.json` 里两个字段都不存在（选择器没被改过时不会写）。→ 两个选择器都在初始化时兜底写一次 `ui_state`，日程侧新增 `schStudents` 字段与咖啡厅对齐。

### 2.2 券分配 `fitCounts`（待移植）

纯函数，按关卡顺序贪心分配余额，目前是前端 12 行 JS，需移植成 Python 并补 3 个用例（余券足够 / 不足 / 配置全 0）。

### 2.3 `stopped` 语义混用（2026-10-28 复核新增）

后端 10 处 `stopped` 赋值混了两种性质，前端 5 处（`index.html:1165`、`1170`、`1445`、`1644`、`1807`）一律打 `err`：

| 性质 | 实际文案 | 应判为 |
|---|---|---|
| 正常终止 | `日程券已用尽`、`挑战券已用尽`、`最高关 X 未三星`、`名册缺少 ServerId` | `ok` / `skip` |
| 真失败 | `Zone X 中断：{e}`、`扫荡失败`、`邀请到 X 号厅失败` | `fail` |

这是"一键清每天结尾一行红字"的**总根源**，比 10-26 修的 arena/shop 两处更根本。
→ 拆成 `stopReason`（文案）+ `stopKind`（`'done' | 'error'`），前端按 kind 上色；后端化时 runner 直接映射到三态，不必再靠文案猜。

## 3. 目标架构

### 3.1 任务状态对象（单例，内存态）

```python
_daily = {
    'running': False,
    'dry': False,
    'startedAt': None,      # '2026-10-26T17:00:00+08:00'
    'finishedAt': None,
    'current': None,        # 正在执行的 key
    'stopRequested': False,
    'order': [],            # 本次执行顺序（快照，执行中改配置不影响）
    'steps': [],            # 见下
}

# 每个 step
{
    'key': 'bounty', 'label': '悬赏通缉',
    'status': 'ok' | 'skip' | 'fail' | 'abort' | 'running' | 'pending',
    'reason': '券不足 6 张，按 6 张执行' | '配置为 0' | '33004 rid 链断裂',
    'startedAt': ..., 'ms': 1834,
    'log': ['[悬赏] ChaserA 5-3 ×2 → 券余 4；...'],   # 该模块自己的输出行
}
```

`status` 沿用 autopcr 的思路但只保留必要档位：

| 状态 | 语义 | 前端显示 |
|---|---|---|
| `ok` | 执行成功 | ✓（绿） |
| `skip` | 前置条件不满足/已做过 | – 跳过（灰） |
| `fail` | 该模块出错，继续跑下一个 | ✗（红） |
| `abort` | 致命错误，整个任务中止 | ⛔（红，后续标 `pending`） |

**什么算 abort**：连续 2 个模块失败且错误含 `33004`/`33005`/`过期`/`time over` → 判定会话彻底失效，中止。避免 10 个模块各撞一次墙、还各触发一次重登。（`_looks_like_session_dead()` 为新增辅助函数，判定规则与 `call_session` 里的重登条件一致。）

### 3.2 接口（3 个）

```
POST /api/daily/run
  body: { dry?: bool, order?: string[], only?: string[], force?: bool }
  → 200 {ok: true, startedAt, order}
  → 200 {ok: false, skipped: true, error: "正在执行中"}      # 复用昨天的 skipped 语义

GET  /api/daily/status
  → 200 整个 _daily 快照（纯内存读，**不碰 _sess_lock**）

POST /api/daily/stop
  → 200 {ok: true, stopRequested: true}                     # 当前模块跑完即停
```

`dry=true` 时：只做「读状态 + 计算计划」，**不调用任何写接口**，每步 `log` 里写"将要执行什么"。用于上线前验证顺序和参数，不必真清票。

### 3.3 执行器

```python
def _daily_worker(order, dry):
    _daily.update(running=True, dry=dry, order=order, steps=[])
    _daily['steps'] = [{'key': k, 'label': LABELS[k], 'status': 'pending', 'log': []} for k in order]
    fails_in_a_row = 0
    try:
        for step in _daily['steps']:
            if _daily['stopRequested']:
                step['status'] = 'skip'; step['reason'] = '用户停止'
                continue
            step['status'] = 'running'
            _daily['current'] = step['key']
            t0 = time.time()
            try:
                res = _RUNNERS[step['key']](step['log'], dry)      # (status, reason) 或抛异常
                step['status'], step['reason'] = res
                fails_in_a_row = fails_in_a_row + 1 if step['status'] == 'fail' else 0
            except _DailyAbort as e:
                step['status'], step['reason'] = 'abort', str(e)[:200]
                for s in _daily['steps']:
                    if s['status'] == 'pending':
                        s['status'] = 'skip'; s['reason'] = '任务已中止'
                break
            except Exception as e:
                logger.exception('[一键清] %s 失败', step['key'])
                step['status'], step['reason'] = 'fail', str(e)[:200]
                fails_in_a_row += 1
                if fails_in_a_row >= 2 and _looks_like_session_dead(str(e)):
                    raise _DailyAbort(str(e))
            finally:
                step['ms'] = int((time.time() - t0) * 1000)
    finally:
        _daily.update(running=False, current=None,
                      finishedAt=datetime.datetime.now().astimezone().isoformat(timespec='seconds'))
        _log_line(f"[一键清] 结束：{_summary(_daily['steps'])}", 'ok' if _all_ok(_daily['steps']) else 'err')
```

**模块 runner 的统一签名**：`runner(log: list, dry: bool) -> (status, reason)`。`log.append(...)` 收集该模块输出行，执行结束后一次性落到操作日志（避免几十条小请求）。

### 3.4 与 `_arena_clear` 的关系

`arena` 模块不是「跑完就结束」，它启动的是**已有的后台清票线程**（`_arena_clear`），一键清只需：
- `_arena_clear['running']` 为真 → `('skip', '上一轮清票仍在进行')`
- 否则启动线程 → `('ok', None)`，日志提示"后台清票中，30s/场"

两块状态各自独立，`/api/daily/status` 里 arena 的 step 只表示"是否已启动"，进度看 `/api/arena/clear/status`。前端需要同时轮询两个接口（或后端在 `/api/daily/status` 里内联 arena 进度摘要，更省一次请求——推荐后者）。

## 4. 前端改造

`runAllDaily()` 从「执行器」变成「触发器 + 渲染器」：

```js
async function runAllDaily() {
  if (ALL_RUNNING) return;
  if (!confirm(...)) return;
  const r = await api('/api/daily/run', {method: 'POST',
    headers: {'Content-Type':'application/json'},
    body: JSON.stringify({dry: $('chkDry').checked})});   // chkDry 为新增控件
  if (!r.ok) { log(`[一键清] ${r.error}`, r.skipped ? 'sub' : 'err'); return; }
  startDailyPoll();          // 每 1.5s 拉 /api/daily/status，按 steps 渲染
}
```

- `startDailyPoll()` 只在 `running` 时轮询，`finishedAt` 出现后停
- 首屏加载时先查一次 `/api/daily/status`：若上次任务没跑完（`running` 为真但进程重启过）→ 显示"上次执行被中断"
- 模块卡片仍可单独点（走原有单模块接口），后端 `running` 时单模块接口不拦（用户手动补跑某一步是合理需求）

## 5. 迁移步骤

1. **补数据与语义**：`schStudents` 落 `ui_state`；`fitCounts` 移植 Python 并单测（3 个用例：余券足够/不足/配置全 0）；`stopped` 拆成 `stopReason` + `stopKind`（后端 10 处赋值、前端 5 处上色）
2. **后端加任务框架**：`_daily` 状态对象 + 3 个接口 + `_RUNNERS` 骨架，先只接 `mail` / `mission` / `gift` 三个无参模块
3. **`dry` 模式上线**：前端加"演练"勾选，逐模块核对 dry 的 `log` 输出与实际一致（不发写请求，安全）
4. **接完 10 个模块**：每接一个用 `only=[key]` 单独跑一次
5. **前端切换**：`runAllDaily` 改为触发+轮询，保留 `dry` 勾选一个版本周期
6. **实弹验证一轮**：与旧路径对比同一份 `moduleOrder` 下的结果日志

每一步都可单独回退（前端切换前，后端接口不影响现有流程）。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 后端线程里出错静默 | 任务卡在 running | `finally` 保证复位；`running` 超过 10 分钟视为僵死，`/api/daily/status` 里自动标 fail 并允许重新启动 |
| 会话锁排队 | 清理期间页面读接口变慢 | 轮询接口不碰锁；其余接受（锁粒度单独处理） |
| 顺序快照与拖拽冲突 | 执行中改顺序无效 | 明确设计：`order` 在启动时快照，改配置下次生效 |
| 与手动点单模块冲突 | 同一接口并发调用 | 各模块已有 `running` 标志（如 `CAFE_RUNNING`），冲突时返回 skipped |
| dry 模式被误认为真执行 | 用户以为清完了 | 前端把 dry 结果整体标灰，标题显示「演练结果，未执行」 |

## 8. 实现记录（2026-10-28）

已按本文落地。关键实现点与设计稿的差异：

| 项 | 设计稿 | 实际实现 | 原因 |
|---|---|---|---|
| worker 签名 | `_daily_worker(order, dry)` | `_daily_worker(order)`，dry 存 `_daily_task['dry']` | 状态对象里本来就有，少传一个参数 |
| `/api/daily/run` 的 `force` | 支持强制重启僵死任务 | 未做；僵死时自动放行（`_daily_is_stale()`） | 不需要用户再勾一个开关 |
| arena 进度内联 | 建议并进 `/api/daily/status` | 未做；竞技场卡片本来就有独立轮询 | 内联要同步两份状态，得不偿失 |
| step 字段 | `startedAt` + `ms` | 只留 `ms` | 前端不显示绝对时间 |
| mail 的 dry | 只报意图 | 真读一次 `mail_state()`，报「待领 N 封」 | 空邮箱能直接判 skip，更有用 |

顺带一起做的三件事：

- **`_lock` 删除**：签名转纯 Python 后是纯函数，没有共享状态，`_sdk_post` 里那把锁失去意义。
- **前端 5 个包装函数删除**：`runDailyArena` / `runDailyGift` / `runDailyMail` / `runDailyMission` / `runDailyShop` 只被旧 `runAllDaily` 调用，后端接管后成为死代码；`runDailyBounty` / `runDailyScrim` 同批删除。
- **`stopped` 拆 `stopKind`**：后端 10 处赋值 + 前端 5 处上色（`done`/`null` → 灰，`error` → 红）。

验证记录（2026-10-28）：

- `dry=true` 全量 10 模块跑通：`plan` 列出 10 个 Zone 与目标学生、`bounty`/`scrim` 各算出 6 张分配、`mail` 判 `skip`（确实没邮件）、`shop` 判 `skip`（自动购买未启用）
- 并发保护：任务进行中再次 `POST /api/daily/run` → `{ok:false, skipped:true}`
- `/api/daily/stop` 在空闲时 → `{ok:true, running:false}`
- **未验证**：真实执行（会清票/购买），留给下次日常；`schStudents`/`cafeStudents` 的自动同步需要浏览器首屏执行一次 `ensurePickerPrefs()`

### 8.1 模块拆分（2026-10-28）

`server.py` 从 2738 行回到 2382 行：一键清整块（状态对象 + 10 个 runner + worker + 3 个接口）移到 `webui/daily.py`（约 440 行）。

- `daily.py` 用 `APIRouter`，`server.py` 末尾 `app.include_router(daily.router)`

### 8.2 状态落盘与跨游戏日（2026-10-28）

`webui/daily_state.json`（gitignored）记录任务快照：`gameDay / startedAt / finishedAt / status / dry / order / steps`（不含 log，明细在操作日志 jsonl）。每次任务开始、每步结束、整轮结束各写一次。

**跨天规则**：日常刷新时间是 **本地 04:00**（官网公告「每日凌晨4点将会开放新一日的任务」；wiki 常见问题「國服的服務器重置時間為北京時間(UTC+8)凌晨04:00」，两处一致）。

- `game_day()` 以 04:00 为界：03:59 仍算前一天
- `load_prev()` 发现落盘的 `gameDay` 不是今天 → 标记 `stalePeriod: true`、**删除状态文件**、记一条 info 日志
- 前端 `restoreDaily()` 只在 `prev.status == 'running' && !stalePeriod` 时提示"上次执行被中断"——昨天的中断不会在今天弹提示

实测：把状态文件的 `gameDay` 改成前一天后请求 `/api/daily/status`，返回 `stalePeriod: true` 且文件被清除，日志留 `[load_prev] 一键清：清理跨游戏日的旧状态（2026-10-27）`。
