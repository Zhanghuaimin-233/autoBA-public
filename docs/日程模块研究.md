## 1. 请求模板（24001 AcademyAttendschedule）

```json
{
  "Protocol": 24001,
  "ZoneId": 12,                      // ← 唯一业务字段：学园 Zone 编号（AcademyZoneExcel.Id）
  "Resendable": true,
  "Hash": 103083510071332,           // (24001 << 32) | N；N=当日会话全局计数（auth 起算 N=1）
  "IsTest": false,
  "SessionKey": {
    "AccountServerId": 10000000000,
    "MxToken": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
  },
  "AccountId": 10000000000,
  "OSType": 2
}
```

要点：
- **MxToken 会话级恒定**（同一登录会话内所有请求同一个值；重登后换新）。构造请求直接复用登录后抓到的 MxToken。
- 请求无其他业务参数——ZoneId 即可，学生是"谁在该 Zone 访问就给谁好感"。
- 服务器响应 `ParcelResultDB.AccountCurrencyDB.CurrencyDict["6"]` = 日程券余量（本次消耗后）。

## 2. 机制规则（全部数据实证 + 官方 wiki 佐证）

| 机制 | 数值/规则 |
|---|---|
| 消耗 | 日程券（货币 Id 6）×1 |
| 区域经验 | Type 15，**+100/次**（区域评级 12 级需 4800→MAX 21400） |
| 好感基准 | **25**/人（区域评级 12 级满级；评级 1~10 级=15，11 级=20） |
| Bonus | 25% 概率好感**翻倍**（基准 25→50）；翻倍部分出现在 ExtraRewards |
| 好感对象 | **该 Zone 的访问学生**（ZoneVisitCharacterDBs），仅已招募（ServerId>0）者入账 |
| 好感上限 | 星级锁定：1★/2★=Rank10、3★=20、4★=30、5★=100；**到上限后一切好感来源浪费** |
| 神明文字 | 4~12% 概率掉对应学生神明文字（本次 7 次未触发） |

## 5. 构造实测（2026-10-15 ✅ 完成）

- **自主冷登录链全通**（`ba_session.py`）：yostar Token 长效复用 → auth 新 key 重加密（防去重缓存）→ 资源版本头动态升级 → **REQUEST-ID 链**（每个响应颁发下一个请求的 rid）→ N 逐请求 +1。
- **实弹成功**：`attendschedule ZoneId=61`（崔尼蒂广场区，当日访客花子/初音未来）→ 券 7→6、CharacterDBs 精确 +25（初音未来 195→220、花子 155→180）、ZoneGroup {"61":[141001]}、ExtraRewards 空（Bonus 未触发）。
- **踩坑记录（重要）**：
  - 复用旧 REQUEST-ID → 服务器视为 Resendable 重发，返回上次响应（`Academy_GetInfo` 状态形态），**静默不执行**——曾误判为"Zone 不可做"，实为 rid 缓存假象。
  - 用陌生 uuid 当 rid → 33004 request_id does not match。
  - N 错误同样报 33004（与 10-12 游戏现场一致）。
  - **rid 链 + N 计数 + Token 三者共同构成会话校验，缺一 33004/缓存**。
- **ZoneId 语义**：与 `AcademyDB.ZoneVisitCharacterDBs` 键同一编号空间（小编号 12~112+）；当日访客学生所在的 Zone 即可执行（学生每日 4:00 刷新）；响应 `ZoneScheduleGroupRecords = {ZoneId: [RewardGroupId]}`（RewardGroupId=AcademyZoneExcel.RewardGroupId）。

## 6. 一键清票（2026-10-17 实现）

**目标选择三轮筛选**（`webui/server.py::build_plan`）：

1. **指定学生**：WebUI 勾选的学生。Zone 内只要有一个「指定且未达好感上限」就入选；指定学生已满则该 Zone 不进第一轮（即使同 Zone 其他学生没满）。两个指定学生一满一未满 → 仍入选。
2. **收藏学生**：`CharacterDB.IsFavorite`。规则同第一轮（只看收藏学生是否可涨）。
3. **好感最优**：剩余 Zone 按「预期好感」降序。预期 = Σ(0.75×min(25,剩余经验) + 0.25×min(50,剩余经验))，剩余经验用 `FavorLevelExcel`（Level→升级所需经验）算到星级上限。

执行：按方案顺序调 24001，响应 `ParcelResultDB.AccountCurrencyDB.CurrencyDict["6"]` 归零即停；已执行的 Zone 从 `ZoneScheduleGroupRecords` 排除，可重复点（幂等）。

**数据来源**：学生名册 = `loginsync(1017).CharacterListResponse.CharacterDBs`（174 人，含 FavorRank/FavorExp/StarGrade/IsFavorite）；今日访客 = `getinfo(24000).AcademyDB.ZoneVisitCharacterDBs`。

**券余量坑（2026-10-17 实弹复验）**：客户端**没有独立的余额查询接口**——全部抓包里 0 个 currency 请求；券数只随 `loginsync(1017).AccountCurrencySyncResponse.AccountCurrencyDB.CurrencyDict["6"]` 下发（协议 1003 的响应体）。但这个字段**不可信**：10-17 19:10 清票前它报 0（`UpdateTimeDict["6"]` 停在 10-16 23:12），实弹 attend 后返回 **6**，即当时真实余额是 7。10-11/12/13 三次同样（登录同步报 0，首次 attend 从 7 扣到 6）。推测 4:00 补票不会刷新该 sync 快照（服务端惰性补票），必须有一次消耗动作才回转。
→ **余量只能按「每日 7 张 − 今日已用 Zone 数」估算**（四次实测均为 7 张），最终以 attend 响应为准。`CurrencyExcel.DailyRefillAmount=10` 与国服实测 7 不符，待查。
→ 想要真·只读余额，需要 `Account_CurrencySync(1003)` 的 URL + 混淆名；客户端里这些字符串是运行时解密的，静态镜像中无明文（`/api/*` 与 26 位 obf 均搜不到），暂无低成本获取途径。
